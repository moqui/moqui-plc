# DeviceConfig Semantics

## Core idea

`DeviceConfig` is not a runtime snapshot of a specific device.

It is a reusable configuration or template that is compatible with all devices
of the same `deviceTypeEnumId`.

`DeviceConfigSet` is the analogous composition layer for a device group. It
bundles multiple compatible `DeviceConfig` records into one reusable group-level
template.

`DeviceConfigSetMember` is the associative layer that composes that set.

The `Parameter` rows linked through `Parameter.deviceConfigId` represent the
future values that will be applied, asserted, or compared when that config is
used.

## Consequences

- if a device type already has its base `ParameterDef` catalog, a first
  `DeviceConfig` template is almost completely determined
- all devices of the same `deviceTypeEnumId` can share the same `ParameterDef`
  records
- each atomic device template and its first `DeviceConfig` template should stay
  tightly coupled through the same `ParameterDef` catalog
- each `DeviceGroup` may later get a `DeviceConfigSet` that composes the member
  `DeviceConfig` templates for the grouped atomic devices
- the first `DeviceConfig` generated by the skill should normally be a
  `TEMPLATE` configuration
- the skill does not need to generate many concrete recipes at authoring time
- the user can later clone the template or fill in parameter values in Moqui UI

## Fixed config-input catalog vs complete catalog

The atomic device seed defines the full parameter catalog for that device type.

The first `DeviceConfig` should reuse the same `ParameterDef` records, but it
does not include an arbitrary hand-picked subset.

Instead, it should include a fixed catalog derived from the allowed
configuration-oriented `VAR_INPUT` fields of the corresponding moqui-plc FB.

Practical rule:

- include all and only the FB fields that are declared as `VAR_INPUT` and are
  suitable for recipe/config authoring for that FB type
- exclude every `VAR_IN_OUT`
- exclude feedback inputs, runtime status outputs, references to
  device-tree objects, and transient diagnostic/runtime values
- exclude any `VAR_INPUT` that is actually wired to physical I/O signals in the
  machine, because those are not recipe values
- when a control-like input such as `enable`, `execute`, or similar is
  included, use conservative defaults so that loading the recipe leaves the
  device in `OFF` / `Standby` / non-running state
- store enum-like configuration inputs using their numeric constant value in
  `numericValue`, rather than symbolic labels

Examples:

- `Actuator`
  - include the fixed config-input set such as `actuatorId`, `actuatorName`,
    `actuationType`, `feedbackType`, `model`, `operationType`,
    `enableTime`, `disableTime`, `enablePreset`, `diagnosticsEnable`
  - exclude handshake, feedback, and runtime outputs such as
    `enableRequest`, `enabledSensor`, `fault`
- `ProcessPid`
  - include the fixed config-input set chosen from `VAR_INPUT`
  - exclude runtime/control gate and feedback values such as
    `enable`, `reset`, `feedback`, `outputActual`, `atSetpoint`
- `Axis` / `AxisGroup`
  - include only the fixed scalar `VAR_INPUT` catalog chosen for recipe/config
  - exclude references and device-tree-backed objects such as `master`,
    `slave`, `group`, `triggerInput`, motion profiles, and robotics structures
- digital and analog sensor subtypes such as `DtInputDigitalSensor`,
  `DtOutputDigitalSensor`,
  `DtInputAnalogSensor`, and `DtOutputAnalogSensor`
  - their minimal catalog is feedback-only, so they usually do not need a
    first `DeviceConfig` template at all unless the project adds separate
    calibration/configuration parameters

## Practical workflow

1. create `Device`, `PhysicalDevice`, `DeviceGroup`, `ParameterDef`, `Parameter`
2. derive a first `DeviceConfig` template for the same `deviceTypeEnumId`
3. attach `Parameter` rows to that `DeviceConfig` using the same `ParameterDef`
   catalog already used by the device type
4. create `DeviceConfigSet` when a `DeviceGroup` needs a composed group-level template
5. create `DeviceRuleSet` and `DeviceRule` only when a config or config set must be applied,
   sequenced, or asserted against a logical device

## What the skill should generate

The skill should generate only:

- one initial `DeviceConfig` template
- optionally one initial `DeviceConfigSet` template for each relevant group
- optionally one basic `DeviceRuleSet`
- optionally one basic `DeviceRule` that applies the template to a device

The template should be clearly marked with `TEMPLATE` in `configName`.

## DeviceRuleSet and DeviceRule

`DeviceRule` is the associative entity that applies one `DeviceConfig` to one
logical `Device`, optionally within a status or status-flow scope.

That logical `Device` may represent:

- one `PhysicalDevice`
- one `DeviceGroup`

Compatibility rule:

- `DeviceRule.deviceId` must reference a `Device` whose `deviceTypeEnumId`
  matches the `DeviceConfig.deviceTypeEnumId`

`DeviceRuleSet` sequences multiple rules.

Typical meaning:

- `DeviceRuleSet`
  - orchestration or sequencing container
- `DeviceRule`
  - apply / assert / validate a given config on a specific logical device

In other words:

- `DeviceConfig` is by device type
- `DeviceRule` is by device instance
- `DeviceConfigSet` is by device group
- `DeviceRuleSet` sequences the instance-level bindings

## Recommended defaults

For the first generated template:

- `DeviceConfig.configTypeEnumId = DctApplyConfig`
- `DeviceConfig.purposeEnumId = DcpPrototypeConfig`
- `DeviceConfig.configName = <device-type-or-device-name> TEMPLATE`
- `DeviceRuleSet.purposeEnumId = DrspConfiguration`
- `DeviceRule.ruleTypeEnumId = DrtApplyConfig`
